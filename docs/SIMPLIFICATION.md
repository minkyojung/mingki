## 결정 사항

| 항목 | 결정 |
|---|---|
| 결과물 | 코드 수정안 대신 **상품별 변경 제안서**. 상품마다 영향(변경 필요 · 유지 · 추가 확인 필요), 근거, 변경 내용, 적용 시점, 후속 작업 |
| Agent | **3개.** Requirement(요건 추출) · Product Impact(상품별 영향 판단, 기존 Locate) · Proposal(상품별 변경 제안, 기존 Design) |
| 빠지는 것 | 코드 검색 · 코드 수정안 · 테스트 생성 · 샌드박스 검증 · Draft PR · 작업 티켓, code-mcp |
| 근거 검사 | **남긴다.** 상품 · 규칙 · 법령 근거가 실제 조회 자료와 맞는지 코드로 검사한다. 정답지는 쓰지 않는다 |
| 모르는 것 | 자료에 없는 현재 절차는 지어내지 않고 **"추가 확인 필요"**로 낸다 |
| 사람 확인 | **1번 + 수정 요청.** 제안이 다 나온 뒤 상품별로 반영 / 제외를 고른다. 그 전에 상품 하나씩 수정 요청을 보낼 수 있다. AI는 그 제안의 글(제안 문장 · 조치 · 주의사항)만 다시 쓰고, 판정 · 바꿀 규칙 · 값 · 적용 범위는 바꾸지 않는다 (2절) |
| 실제 반영 | **한다.** 확인한 제안을 상품 규칙 새 버전으로 등록한다. 평가표 MCP 변경 도구 · 대기열 항목을 지키는 단계다 (7절) |
| 역할 · 권한 | **없음.** 로그인(JWT)만 남긴다 |
| DB | 지금 테이블(`products` · `product_rules` · `loan_contracts`)을 그대로 쓴다. 제안 저장용 `rule_proposals`만 추가한다. 화면 문구 · 절차 같은 후속 작업 근거는 상품 문서(`doc://P001` 등)에서 찾는다 |
| 첫 단계 | **DSR 변경 하나로 전 상품을 빠짐없이 판단**하는 것부터 끝까지 동작시킨다 (8절) |

## 2. 흐름

```
업로드 ─▶ ① Requirement Agent: 바뀐 조항 · 적용 범위 · 시행일 · 경과조치 ─(실질 변경 0건)─▶ 종료(NO_CHANGE)
            │ rag-mcp(regulation-mcp): 조항 비교 · 규정 · 상품 문서 혼합 검색
            ▼
        ② Product Impact Agent: 전 상품 · 규칙 조회 → 상품별 영향 판단
            │ business-mcp: 상품 · 규칙 · 규칙 키 목록 · 계약 영향 조회
            ▼
        ③ Proposal Agent: 상품별 변경 제안 작성
            ▼
        근거 검사 (코드) ─(실패, 재시도 남음)─▶ ③ 제안 작성        ← 반복
            ▼
        사용자 확인 [interrupt] ─(전부 제외 · 거절)─▶ 리포트 ─▶ 종료(REJECTED)   ← 상태 저장 · 재개
            │   └(수정 요청, 상품 하나)─▶ ③ 그 제안 글만 다시 작성 ─▶ 근거 · 요청 반영 검사 ─▶ 사용자 확인
            │ 상품별 반영 / 제외
            ▼
        상품 규칙 새 버전 등록      business-mcp 변경 도구 → 확인 기록 검증 → 대기열(재시도 · DLQ)
            ▼
        리포트(최종 보고서) ─▶ 완료(DONE)
```

| 단계 | 노드 | 백엔드 상태 | 화면 표시 |
|---|---|---|---|
| ① 요건 추출 | `requirement_agent` | `EXTRACTING` | 바뀐 조항을 찾는 중 |
| ② 영향 판단 | `product_impact_agent` | `LOCATING` | 상품별 영향을 판단하는 중 |
| ③ 제안 작성 | `proposal_agent` | `DESIGNING` | 변경 제안을 만드는 중 |
| 근거 검사 | `verify` | `VERIFYING` | 제안을 검사하는 중 (n차) |
| 사용자 확인 | `review` | `WAITING_REVIEW` | 제안 확인 필요 |
| 반영 | `apply` | `PUBLISHING` | 상품 규칙에 반영하는 중 |
| 종료 | `report` | `DONE` · `NO_CHANGE` · `REJECTED` · `FAILED` | |

- 수정 요청을 보내면 `WAITING_REVIEW → DESIGNING → VERIFYING → WAITING_REVIEW`로 돌아온다. 이 되돌이는 몇 번이든 할 수 있다 (BACKEND_API 10.3).
- 다시 쓴 결과는 네 가지다. 반영, 반영 불가(원문과 충돌, 예: 35% 대신 30%), 추가 확인 필요(대상 재판단 요청 등), 재작성 실패(이전 본문 유지, 그 상품은 승인 불가 · 제외는 가능).
- `WAITING_REQUIREMENT_APPROVAL` · `HELD`는 없다 (V7에서 지움, BACKEND_API 10.7).
- `EXTRACTING → LOCATING` 직행을 백엔드에서 허용한다 (`chanhyeok/simplify-reset`). 노드 이름(`impact_agent` · `proposal_agent` · `apply`)은 백엔드 상태 매핑에 추가한다.

## 3. 결과물: 상품별 변경 제안

제안 1건 = 상품 1개 × 규칙 1개. 화면용 글과 반영용 값을 함께 둔다.

```json
{
  "product_id": "P001",
  "requirement_id": "REQ-8",
  "rule_id": "R001",
  "rule_key": "DSR_LIMIT",
  "impact": "change_required",
  "current": "DSR 한도 40%",
  "proposed": "DSR 한도 35%",
  "unit": "ratio",
  "current_value": "0.40",
  "proposed_value": "0.35",
  "basis": "개정 제8조",
  "reason": "현재 상품 기준이 개정 한도를 초과함",
  "effective_date": "2026-12-01",
  "transition": "시행일 전 신청분 · 기간 연장은 종전 기준 유지 (부칙 제2조)",
  "follow_up": ["상품 심사 기준 변경", "신청 화면 안내 문구 변경", "상품 설명서 변경"]
}
```

| `impact` | 뜻 | 반영 대상 |
|---|---|---|
| `change_required` | 변경 필요. 기존 규칙이면 `rule_id`, 새 규칙이면 `rule_id` 없음 | 예 |
| `keep` | 유지. 이유 필수 (이미 기준 충족, 적용 제외 대상, 판매 중단 등) | 아니오 |
| `needs_check` | 추가 확인 필요. 적용 대상인데 기준 데이터가 없거나, 숫자로 표현하기 어려운 변경 (설명 기록 보관 등) | 아니오. 리포트 · 후속 작업으로 |

DSR 시나리오 정답 요약 (#21, 상품 12개 전부 판정):

| 판정 | 상품 | 판단 포인트 |
|---|---|---|
| `change_required` | P001 · P002 · P008 | 0.40 → 0.35 (P008은 증액 대환 기준) |
| `change_required` | P005 | **단위 함정**: `percent` 규칙이라 40 → 35 |
| `change_required` | P007 | **키 이름 함정**: `MAX_DSR_RATIO` |
| `change_required` | P011 | **옛 버전 함정**: 종료된 R074(0.50)가 아니라 현재 R075를 바꾼다 |
| `keep` | P003 · P004 | 이미 신 기준 이하 (0.35 · 0.30) |
| `keep` | P006 · P009 | 적용 제외 (소액 · 사업자대출, DSR 관리기준) |
| `keep` | P012 | 판매 중단, 계약 당시 기준 (운영기준 제21조) |
| `needs_check` | P010 | 적용 대상인데 현재 DSR 기준 행이 없음 |

## 4. 근거 검사 (정답지 사용 금지)

검사는 **입력(규정 diff, 상품 · 규칙 조회 결과)만으로 결정되는 것**을 본다. 정답지를 읽으면 Agent 입력에서 정답 힌트를 뺀 원칙(#4)과 충돌하고, 반복 루프가 자기채점이 된다.

| 순서 | 검사 | 예 |
|---|---|---|
| 1 | **단위 변환이 맞는가** (시연에서 반복이 돌게 하는 1순위) | 신 조항 "35%" → `ratio`면 0.35, `percent`면 35 (P005). 단위를 틀리면 실패 → 재작성 |
| 2 | 인용한 조항이 `diff_versions`에서 실제로 바뀐 조항인가 | 제8조 · 제15조 · 제15조의2 |
| 3 | 상품 · 규칙 · 지금 값이 조회 결과와 같은가, 현재 유효한 행인가 | R001의 지금 값이 0.40인가. 종료된 R074를 고치지 않았는가 |
| 4 | 날짜가 맞는가 | 새 행 `effective_from` = 시행일(2026-12-01), 기존 행 `effective_to` = 전날(2026-11-30) |
| 5 | 이미 신 기준을 충족한 규칙에 변경 제안을 하지 않았는가 | P003 0.35 · P004 0.30은 `keep` |
| 6 | 모든 상품에 판정이 하나씩 있는가 | 12개 중 빠진 상품이 없어야 한다 |

**함정 판단은 검사가 아니라 LLM의 몫이다.** 같은 0.40이지만 LTV, 적용 제외 대상(소액 · 사업자), 판매 중단 상품 같은 판단은 LLM이 근거와 함께 내고, 맞았는지는 **평가 스크립트가 정답지와 비교해 점수로** 보여준다.

## 5. 난이도: Agent의 가치가 보이게

| 항목 | 내용 |
|---|---|
| DSR 함정 (M1) | 단위(P005 `percent`), 키 이름(P007 `MAX_DSR_RATIO`), 옛 버전(P011 R074), 적용 제외(P006 · P009), 판매 중단(P012), 기준 데이터 없음(P010). 키워드 검색으로는 갈리지 않는다 |
| 후속 작업 (M1 가산) | 상품 문서에서 "DSR 40%" 화면 문구 · 심사 절차를 찾아 `follow_up`에 적는다 (P001 · P005 · P008 · P011 번역본 3종) |
| 경과조치 영향 | 계약 영향 조회로 종전 기준이 유지되는 계약을 함께 보인다. 시행일 전 신청 9건(C0004 등), **DSR 구간(0.35 초과 0.40 이하) + 만기가 시행일 이후 → C0006**(연장 시 종전 한도, 부칙 제2조 ②) · C0068(판매 중단 상품) |
| 고령자 기준 (M3) | R010 `ELIGIBLE_MIN_AGE`: 키 이름에 SENIOR가 없어 키워드 검색으로는 못 찾는다. 정답지 2단계에서 확정 |
| 제15조의2 새 규칙 (M3) | 전 상품 `SENIOR_EXPLANATION_REQUIRED = true`(bool)를 `rule_id` 없는 변경 필요로 제안한다. 체결일 기준(부칙 제3조)은 제안 설명에 적는다. 설명 기록 보관 · 확인 전 체결 금지는 `needs_check` + 후속 작업 |

| 가산점 대기열 (10) | ✅ | 상품 규칙 반영을 대기열 작업(`APPLY_RULE_VERSION`)으로, 재시도 · DLQ(#29 · #33). #35 실행에서 실패 주입 1건이 2회차에 성공 |

반영 단계를 빼면 MCP 변경 도구 · 대기열 작업이 사라지고, 근거 검사가 실패해도 다시 쓰는 루프가 없으면 반복이 사라진다. 그래서 반영과 반복을 남긴다.
